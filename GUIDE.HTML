FPTUI User Guide

FPTUI is a text-mode user interface for Free Pascal on 32-bit DOS (go32v2). Forms and controls follow Lazarus (and FPTEGL's DUI): you make a TForm descendant, put TButtons, TEdits and friends on it, hook up OnClick and friends, and call Application.Run. Everything is drawn with text cells in the Turbo Vision / Technojock's toolkit style.

The screens in this guide are not mock-ups. GUIDESHOT.PAS builds each example with the code shown and records what the screen shows.

Getting started

Put the TUI units (TUI*.PAS, TUI.INC) where the compiler finds them and build for DOS:

fpc -Tgo32v2 -O2 myprog.pas

Like every go32v2 program it needs a DPMI host: CWSDPMI.EXE on the PATH (Free Pascal's go32v2 install has one) or HDPMI32 -r.

A program is a project file and one unit per form, just as in Lazarus. The project:

program MyProg;

{$mode objfpc}{$H+}

uses
  TUICtrl, MainForm;

begin
  Application.Title := 'My program';
  Application.Initialize;
  Application.CreateForm(THelloForm, HelloForm);
  Application.Run;
end.

The form unit. The constructor makes the controls here; they can also come from an .lfm file, as in Lazarus (see Forms from .lfm files):

unit MainForm;

{$mode objfpc}{$H+}

interface

uses
  Classes, SysUtils, TUICtrl, TUIStd;

type
  THelloForm = class(TForm)
    NameLabel: TLabel;
    NameEdit: TEdit;
    GreetButton: TButton;
    procedure GreetButtonClick(Sender: TObject);
  public
    constructor Create(AOwner: TComponent); override;
  end;

var
  HelloForm: THelloForm;

implementation

constructor THelloForm.Create(AOwner: TComponent);
begin
  inherited Create(AOwner);
  Caption := 'Hello';
  SetBounds(2, 1, 40, 8);              { Left, Top, Width, Height in cells }

  NameEdit := TEdit.Create(Self);
  NameEdit.Parent := Self;
  NameEdit.SetBounds(9, 1, 26, 1);
  NameEdit.Text := 'World';

  NameLabel := TLabel.Create(Self);
  NameLabel.Parent := Self;
  NameLabel.Left := 2;
  NameLabel.Top := 1;
  NameLabel.Caption := '&Name:';
  NameLabel.FocusControl := NameEdit;  { Alt+N goes to the edit field }

  GreetButton := TButton.Create(Self);
  GreetButton.Parent := Self;
  GreetButton.SetBounds(13, 3, 12, 2);
  GreetButton.Caption := '&Greet';
  GreetButton.Default := true;         { Enter anywhere on the form }
  GreetButton.OnClick := @GreetButtonClick;

  ActiveControl := NameEdit;
end;

procedure THelloForm.GreetButtonClick(Sender: TObject);
begin
  ShowMessage('Hello, ' + NameEdit.Text + '!');
end;

end.

The first form created is the main form; Application.Run shows it, and closing it ends the program. Every control is owned by the form (Create(Self)) and freed with it; Parent says where it sits.

TUIDEMO.PAS (with MAINFRM.PAS and the other *FRM.PAS units) shows every control; TUITEST.PAS drives the demo with posted keys and mouse clicks and checks the results.

Cells and colours

Positions and sizes are character cells: Left, Top, Width, Height count columns and rows.

  • A form's Left/Top are screen cells and its Width/Height include the frame. ClientWidth/ClientHeight are the inside.
  • A control's Left/Top are relative to its parent's client area (the inside of the frame, below a window's menu bar).
  • Buttons are two rows high: the face and the shadow.

TColor is one of the 16 text colours. The LCL names map onto them, and the text-mode names are there too:

Value LCL name Text mode name Value LCL name Text mode name

3 clTeal clCyan 11 clAqua clLightCyan

clDefault means "the theme decides". Color is the background, Font.Color the text:

StatusLabel.Font.Color := clBlue;
InfoForm.Color := clCyan;

The theme (Theme in TUICTRL) holds every colour the controls use; SetColorTheme and SetMonoTheme fill it (mono is picked on MDA/ Hercules screens).

Forms

F := TForm.CreateNew(nil);           { a form without a class of its own }
F.Caption := 'Settings';
F.SetBounds(0, 0, 38, 8);
F.Position := poScreenCenter;         { poDesigned, poScreenCenter, poMainFormCenter... }
F.BorderStyle := bsDialog;            { bsSizeable (default), bsSingle, bsDialog, bsNone }
To Use
show a window F.Show (it comes to the front and is active)
hide it F.Hide or F.Close
run it as a dialog if F.ShowModal = mrOk then ...
end a dialog set F.ModalResult, or a button's ModalResult
free it after closing OnClose: CloseAction := caFree
maximize F.WindowState := wsMaximized
catch keys first F.KeyPreview := true and OnKeyDown

A dialog the usual way:

OkButton.ModalResult := mrOk;          { a click closes the dialog with mrOk }
OkButton.Default := true;              { Enter }
CancelButton.ModalResult := mrCancel;
CancelButton.Cancel := true;           { Esc }
if F.ShowModal = mrOk then SaveSettings;
F.Free;

Events: OnCreate (after the constructor), OnShow, OnHide, OnActivate, OnDeactivate, OnClose, OnCloseQuery (CanClose := false keeps it open), OnResize, OnKeyDown, OnKeyPress.

bsSizeable forms can be resized and maximized: drag the lower right corner, click [↑] or double click the title; from the keyboard Ctrl+F5, then arrows move and Shift+arrows size. Constraints.MinWidth etc. limit it. Drag a window by its title; [■] closes it.

Forms from .lfm files

A form's controls can come from an .lfm file instead of the constructor. The syntax is Lazarus's text .lfm (object Name: TClass, Property = value, nested objects, end), and it maps one to one onto FPTUI: every Left, Top, Width and Height is in character cells (columns and rows), exactly as in code. Nothing is scaled.

The form unit only lists the controls and the event handlers; no constructor is needed:

unit LfmDemo;

{$mode objfpc}{$H+}

interface

uses
  Classes, SysUtils, TUICtrl, TUIStd, TUIList, TUIMenu, TUIExt;

type
  TLfmForm = class(TForm)
    NameLabel: TLabel;               { set by the .lfm, by name }
    NameEdit: TEdit;
    HelloButton: TButton;
    SizeGroup: TRadioGroup;
    StatusBar1: TStatusBar;
    procedure NameEditChange(Sender: TObject);   { found by name too }
  end;

var
  LfmForm: TLfmForm;

implementation

procedure TLfmForm.NameEditChange(Sender: TObject);
begin
  StatusBar1.Panels[1].Text := 'Name: ' + NameEdit.Text;
end;

end.

and LFMDEMO.LFM next to it says where everything is and how it is set up:

object LfmForm: TLfmForm
  Left = 3
  Top = 1
  Width = 70
  Height = 22
  Caption = 'A form from LFMDEMO.LFM'
  Position = poScreenCenter
  ActiveControl = NameEdit
  object NameLabel: TLabel
    Left = 1
    Top = 1
    Caption = '&Name:'
    FocusControl = NameEdit
  end
  object NameEdit: TEdit
    Left = 9
    Top = 1
    Width = 30
    Height = 1
    Anchors = [akTop, akLeft, akRight]
    Text = 'World'
    OnChange = NameEditChange
  end
  object SizeGroup: TRadioGroup
    Left = 1
    Top = 5
    Width = 20
    Height = 5
    Caption = '&Size'
    ItemIndex = 2
    Items.Strings = (
      'Small'
      'Medium'
      'Large'
    )
  end
  object StatusBar1: TStatusBar
    Panels = <
      item
        Text = '~F2~ Hello'
        Width = 12
      end
      item
        Text = 'Ready'
      end>
  end
end

Application.CreateForm(TLfmForm, LfmForm) (or TLfmForm.Create) reads it. TForm.Create looks for the form's .lfm in this order:

  1. text built into the program with RegisterFormText;
  2. a file named with RegisterFormFile(TLfmForm, 'FORMS\MAIN.LFM');
  3. <unit name>.lfm, the Lazarus convention (LfmDemo -> LFMDEMO.LFM), in the current folder or the program's folder.

With none found the form is empty, as before. A form class can still have a constructor: it runs after inherited Create has read the .lfm.

To build the .lfm into the program, so no file is needed next to it, use LFM2INC (below).

LFM2INC: building an .lfm into the program

LFM2INC turns an .lfm file into an include file (.LFI) that holds the same text as one Pascal string constant. The program then carries the form with it, and TForm.Create finds it before it looks for any file.

Building the tool. It is a small console program that uses only Classes and SysUtils; build it once, for DOS or for the machine you build on:

fpc -Tgo32v2 -O2 lfm2inc.pas     (DOS: LFM2INC.EXE, needs a DPMI host)
fpc -O2 lfm2inc.pas              (Windows / Linux, if you build there)

Running it.

LFM2INC form.lfm [form.lfi]
Argument Meaning
form.lfm the .lfm to read
form.lfi the include file to write; left out: the same name with .LFI (ABOUTLFM.LFM -> ABOUTLFM.LFI)

It prints the name it wrote and the number of lines, for example ABOUTLFM.LFI: 29 lines. Run without arguments it shows the usage line.

What it writes. One string expression, a line per .lfm line, quotes doubled, each line ending in #10:

{ ABOUTLFM.LFI - made by LFM2INC from ABOUTLFM.LFM }
'object AboutForm: TAboutForm'#10 +
'  Left = 0'#10 +
'  Top = 0'#10 +
'  Width = 46'#10 +
'  Caption = ''About'''#10 +
...
'end'#10

Using it. Register the text in the form unit's initialization section. The form class stays as it was: fields for the controls, methods for the events, no constructor:

unit AboutLfm;

{$mode objfpc}{$H+}

interface

uses
  Classes, SysUtils, TUICtrl, TUIStd;

type
  TAboutForm = class(TForm)
    InfoLabel: TLabel;
    OkButton: TButton;
  end;

implementation

initialization
  RegisterFormText(TAboutForm, {$I ABOUTLFM.LFI});
end.
procedure TMainForm.AboutClick(Sender: TObject);
var f: TAboutForm;
begin
  f := TAboutForm.Create(nil);     { reads the built-in text }
  try
    f.ShowModal;
  finally
    f.Free;
  end;
end;

When you change the form. Edit the .lfm, run LFM2INC again, then rebuild: the .LFI is a copy, the compiler does not look at the .lfm. A batch file keeps the steps together:

@echo off
rem MAKE.BAT - the .lfm files into include files, then the program
lfm2inc ABOUTLFM.LFM
lfm2inc OPTIONS.LFM
fpc -Tgo32v2 -O2 myprog.pas

File or built in?

.lfm file next to the program built in with LFM2INC
how nothing to do: <unit name>.lfm is found, or RegisterFormFile RegisterFormText(TForm1, {$I FORM1.LFI})
change a form edit the .lfm, run the program again edit, run LFM2INC, rebuild
ship the .EXE and its .lfm files the .EXE alone
good for trying layouts quickly a finished program

Both can be mixed. Built-in text wins over a file, so a finished program uses its built-in forms; leave out the RegisterFormText line (for example in a test build) and the .lfm files are read instead.

Notes:

  • The .LFI is plain Pascal: an .lfm of any size works (the constant is joined from one literal per line).
  • Characters outside ASCII (box drawing, accented letters) are copied as they are; keep the .lfm in the code page the program shows (CP437 on DOS).
  • The .lfm is checked when the form is created, not by LFM2INC: a typing error shows up as an exception (or, for an unknown property, a line in LfmWarnings) when the program runs. LFMTEST.PAS shows how to test forms automatically.

What an .lfm can hold:

In the .lfm Example
any published property Caption = 'Hello', Default = True, MaxLength = 4
enums and sets Align = alClient, Anchors = [akTop, akLeft, akRight], Options = [goVertLine, goEditing]
colours and modal results by name Font.Color = clRed, Color = clCyan, ModalResult = mrOK
sub-properties Font.Color, Constraints.MinWidth
lists of strings Items.Strings = ( 'a' 'b' ), Lines.Strings = (...)
collections StatusBar.Panels = < item ... end >, ListView.Columns = < ... >
references to other components FocusControl = NameEdit, Menu = MainMenu1, Action = actHello, ActivePage = NotesSheet, PopupMenu = EditMenu
events: the form's published methods OnClick = HelloButtonClick
nested objects controls inside panels, group boxes and tab sheets; tab sheets inside a page control; menu items inside a menu or item; actions inside an action list; timers, dialogs and menus anywhere
shortcuts numbers, as Lazarus writes them: ShortCut = 113 is F2, 16465 is Ctrl+Q (scCtrl 16384 + Ord('Q'))

Not in an .lfm (set them in OnCreate): string grid cells and column widths, list view items, tree view nodes, check list box check marks.

A property the control does not have (DesignTimePPI, ParentFont...) is skipped and noted in LfmWarnings; with LfmStrict := true it is an error instead. ReadFormText(Form, Text) and ReadFormFile(Form, Name) read an .lfm into any existing form. LFMTEST.PAS checks all of this.

Menus and status bars

Menus and status bars work at two levels. On the screen the menu bar takes the top row and the status bar the bottom row; forms live on the desktop between them:

ScreenMenu := TMainMenu.Create(Self);
ScreenMenu.Items.Add(NewSubMenu('&File', 0, '', [
  NewItem('E&xit', ShortCut(Ord('X'), [ssAlt]), false, true, @ExitClick, 0, '')]));
ScreenMenu.Items.Add(NewSubMenu('&Window', 0, '', [
  NewItem('&Tile', 0, false, true, @TileClick, 0, '')]));
ScreenMenu.Items.Add(NewSubMenu('&Help', 0, '', [
  NewItem('&About', 0, false, true, @AboutClick, 0, '')]));
Application.Menu := ScreenMenu;

ScreenStatus := TStatusBar.Create(Self);   { no Parent: the screen's }
ScreenStatus.Panels.Add.Text := '~F1~ Help';
ScreenStatus.Panels.Add.Text := '~F10~ Menu';
ScreenStatus.Panels.Add.Text := '~Alt+X~ Exit';
Application.StatusBar := ScreenStatus;

In a window, Menu puts the bar under the title, and a status bar with the form as Parent takes the last row:

FileMenu := TMenuItem.Create(Self);        { item by item, as a .lfm does }
FileMenu.Caption := '&File';
Menu1 := TMainMenu.Create(Self);
Menu1.Items.Add(FileMenu);
NewItem1 := TMenuItem.Create(Self);
NewItem1.Caption := '&New';
NewItem1.ShortCut := ShortCut(Ord('N'), [ssCtrl]);
NewItem1.OnClick := @NewClick;
FileMenu.Add(NewItem1);
FileMenu.Add(NewLine);
Menu := Menu1;

Status := TStatusBar.Create(Self);
Status.Parent := Self;                     { Align alBottom }
Status.Panels.Add.Text := '~F10~ Menu';
Status.Panels.Add.Text := 'Ln 1 Col 1';

Code editor

TSynEdit (TUISYNED) is an editor for program text, with syntax colouring from a highlighter (TUISYN). The names follow Lazarus's SynEdit.

Editor.Lines.LoadFromFile('HELLO.PAS');

begin
  Status.Panels[0].Text := 'Ln ' + IntToStr(Editor.CaretY) + ' Col ' + IntToStr(Editor.CaretX);
end;

The editor. No word wrap (long lines scroll sideways), a gutter with line numbers, both scroll bars. As in the Turbo Pascal and QBasic editors the caret may stand past the end of a line; typing there fills the gap with spaces. Tabs in the text become spaces (TabWidth, default 8).

Lines, Text, Highlighter, ReadOnly, Modified, InsertMode, TabWidth, BlockIndent, WordStarKeys, Options (eoScrollPastEol, eoTabsToSpaces, eoKeepCaretX, eoAutoIndent, eoBackspaceUnindents), Gutter (Visible, ShowLineNumbers, Color, TextColor), SelectedColor, Color / Font.Color (the text's own colours), CaretX, CaretY, CaretXY (1 based), TopLine, LeftChar, LinesInWindow, CharsInWindow, BlockBegin, BlockEnd, SelAvail, SelText, SelectAll, SelectWord, SelectLine, ClearSelection, CopyToClipboard, CutToClipboard, PasteFromClipboard, ClearAll, LoadFromFile, SaveToFile, BeginUpdate / EndUpdate; OnChange, OnStatusChange (caret, selection, Modified, InsertMode).

Keys: arrows, Home (the first non-blank, again: column 1), End, Ctrl+Home/End, PgUp/PgDn, Ctrl+Left/Right (words), Ctrl+Up/Down (scroll), Shift+ any of them selects; Enter, Tab, Backspace, Del, Ins, Ctrl+Y (delete the line), Ctrl+A, Ctrl+C/X/V, Ctrl+Ins, Shift+Del, Shift+Ins, and the Turbo / WordStar keys below. Mouse: click, drag, double click (a word), a click in the gutter (the line), the scroll bars, the wheel.

Undo and redo. Every action is one undo step: an Enter with its indent, a paste over a selection, a block indent, a Ctrl+K V move. Typing goes back a word at a time. Undo puts the caret and the selection back where they were; undoing to the last save makes the text unmodified again (Modified := false marks that point, SaveToFile does it too). Text set from code (Text, Lines, LoadFromFile) clears the history.

Key Does
Ctrl+Z, Alt+Backspace undo
Ctrl+Shift+Z, Alt+Shift+Backspace redo

Undo, Redo, CanUndo, CanRedo, UndoCount, ClearUndo, MaxUndo (1024 changes; the oldest steps go first), and BeginUndoBlock / EndUndoBlock to make several edits from code one step.

Indenting. With eoAutoIndent (on) Enter indents the new line like the line above. With eoBackspaceUnindents (on) Backspace in the leading blanks goes back to the indent of the nearest line above with a smaller one. Tab on a selection moves its lines right by BlockIndent (2), Shift+Tab moves them (or the caret's line) left; the selection stays. IndentBlock and UnindentBlock do it from code.

Turbo blocks and quick moves. Ctrl+K and Ctrl+Q wait for a second key (with or without Ctrl); PendingPrefix says which (the code editor window shows ^K in its status bar). A block marked with Ctrl+K B and Ctrl+K K stays while the caret moves, as in Turbo Pascal; the block commands use the selection when there is one.

Hints

ShowHint := true;                      { the form: every control with a Hint }
OpenBtn.Hint := 'Open|Open a file';    { short | long }

When the mouse rests on a control for Application.HintPause (800 ms) the short part shows under it for HintHidePause (5 s); a key or a move away puts it away. Status bars with AutoHint show the long part: the focused control's, the tool button's under the mouse, or the menu item's. Application.ShowHint := false switches hint windows off.

The application

Windows. F6 and Shift+F6 go to the next and previous window. Application.Tile and Application.Cascade arrange the visible windows in the desktop; Application.Forms[], Screen.Forms[], Screen.FormCount, Screen.ActiveForm list them.

Application.Cascade;
Application.Tile;

Text modes. Set TUITextCols / TUITextRows before Application.Initialize, or switch while running:

if not Application.SetTextMode(132, 50) then
  Application.SetTextMode(80, 50);

80 x 25/28/43/50 work on VGA; 80 x 60 and 132 x 25/43/50/60 need a VESA text mode (or the S3/Cirrus 132 x 25 and 132 x 43 modes, which DOSBox has). The screen bars move, forms stay on the screen, maximized forms fill the new desktop, then Application.OnScreenResize runs.

The clipboard. Clipboard.AsText (inside the program); edits and memos use it for Ctrl+C/X/V.

Exceptions. An exception in an event shows an error box and the program goes on; Application.OnException replaces the box.

The mouse wheel (CuteMouse 2 and other drivers with the wheel API): lists, memos, grids, views and scroll boxes scroll; scroll bars, track bars and spin edits move. OnMouseWheel on any control can take it first.

Idle, loops, tests. Application.OnIdle runs when there is nothing to do. Application.ProcessMessages handles what is waiting. TUIPostKey, TUIPostChar, TUIPostString, TUIPostMouse, TUIPostClick and TUIPostWheel feed input as if typed or clicked; TUITEST.PAS uses them.

Speed. Everything is drawn into a buffer of the screen; once per loop only the cells that changed go to video memory. Repainting a whole form that did not change writes nothing.
